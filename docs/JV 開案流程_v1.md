## 名詞說明
- **Story Point：** 即 SP 點數。代表需求的開發工作量。點數越高，代表需求越複雜、所需時間越長。

## 角色說明
| **角色** | **說明** |
| -- | -- |
| **Scrum Master** | 促進 Scrum 流程的實施，移除團隊障礙，並確保團隊高效運行。|
| **強合智慧** | 負責需求分析、系統規劃、設計開發、測試修正、系統部署及後續維運支援等相關技術執行作業。|

# Phase 1 — 需求確認
## 1.1 需求提案
### 目的

==**若由強茂 IT 自行開發，則不適用此開案流程。**==

# Phase 2 — MVP 架構確認
### 目的 
依據需求訪談結果定義最小可行產品（MVP）範圍，明確界定本階段優先開發之功能與系統邊界，並據以產出需求規格文件（PRD）及初步系統網址，供使用者進行初步介面與流程驗證，作為後續系統調整與開發之依據。

==**MVP 階段之需求調整以三次為限（含第一次），超過次數之調整內容，如後續確認開案，將於開案後再行評估與處理；如未開案，則酌收 SP 點數。**==

### 階段產出
1. MVP 範圍定義書。
2. PRD 需求規格文件。
3. MVP 初步系統網址。

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 | 
| -- | -- | -- |  -- |
| Scrum Master | ○ | 依案件緊急程度評估是否參與。 |
| 強合智慧 | ● | 1. 依需求訪談結果規劃 MVP 架構與功能內容。 </br> 2. 撰寫 MVP 範圍定義書及 PRD 需求規格文件。 </br> 3. 建置 MVP 初步系統網址供使用者驗證。 </br> 4. 依驗證結果評估後續調整方向與開發規劃。 | 1. MVP 範圍定義書 </br> 2. PRD 需求規格文件 </br> 3. MVP 初步系統網址 |
| 強茂 IT | ★ | 1. 協調使用者與強合智慧之間的需求確認與溝通。 </br> 2. 審視 PRD 文件及 MVP 內容是否符合需求方向。 </br> 3. 彙整驗證回饋，作為後續調整與開發依據。 | |
| 強茂使用者 | ● | 1. 確認需求訪談內容與PRD 需求規格文件是否一致。 </br> 2. 協助確認 MVP 範圍、功能優先順序及驗證重點。 </br> 3. 針對 MVP 初步系統介面與流程提供回饋意見。 | |

### 階段產出
1. 專案開案單（檢附需求方主管簽核證明）。
2. BPM PJM02 資訊服務申請單。
    - 審核項目：需求明確性、技術可行性、SP 合理性、預算、時程。

- ✅ **確認通過** → 進入 Phase 4 — 開發，進行完整 APP 開發。

# Phase 4 — 開發
### 目的 
依據 PRD 需求規格文件及每次使用者測試回饋結果，進行系統迭代開發與持續交付，並視專案需求不定期召開討論會議，針對功能調整、需求變更與實作方式進行確認，以確保開發內容符合需求方向與專案目標。

:::danger
⚠️ **注意：** 
強合智慧完成 APP 交付或程式修正後，**需求單位應於 10 個工作天內完成確認並回覆**；如逾期未回覆，則該專案將將予以暫停，並由開發團隊優先處理其他專案需求，原專案則順延辦理。
:::


### 階段產出
1. 衝刺待辦清單 ( Sprint Backlog )。
2. SDD 系統設計文件。
3. APP 交付。

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 | 
| -- | -- | -- | -- |
| Scrum Master | — | | |
| 強合智慧 | ★ | 1. 依 PRD 與回饋結果規劃 Sprint Backlog 與開發內容。 </br> 2. 撰寫與更新 SDD 系統設計文件。 </br> 3. 執行系統開發、功能調整與階段性交付。 </br> 4. 參與討論會議。 | 1. 衝刺待辦清單 </br> 2. SDD 系統設計文件</br> 3. APP|
| 強茂 IT | ● | 1. 彙整使用者測試回饋與需求調整事項。  </br> 2. 協調使用者與強合智慧確認 Sprint 開發內容。  </br> 3. 追蹤開發進度、確認交付項目與需求一致性。 </br> 4. 召開或安排討論會議，協助釐清需求與調整方向。 |
| 強茂使用者 | ● | 1. 提供使用者測試回饋與調整建議。 </br> 2. 參與必要討論會議，確認開發成果是否符合使用需求。 | |

# Phase 5 — 驗收
### 目的 
由使用者透過驗收作業確認系統開發成果是否符合需求規格文件、業務流程及使用需求，並就功能完整性、操作正確性與交付內容進行檢核，作為系統上線、結案之依據。

### 階段產出
1. BDD 行為驅動開發文件。
2. TDD 測試驅動開發文件。
3. 測試報告。

### 驗收結果
> 於 JV 需求管理平台進行簽核。
- ✅ **確認通過** → 進入 Phase 6 — 結案。
- ❌ **退回修改** → 回到 Phase 4 — 開發，重新調整。

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 | 
| -- | -- | -- | -- |
| Scrum Master | — | | |
| 強合智慧 | ● | 1. 針對驗收問題進行分析、修正與回覆。 </br> 2. 依驗收結果完成必要調整，作為後續上線或結案依據。 | 1. BDD 行為驅動開發文件。 </br> 2. TDD 測試驅動開發文件。 </br> 3. 測試報告。 |
| 強茂 IT | ● | 1. 作為使用者與強合智慧之間的溝通窗口，追蹤驗收進度。 | 於 JV 平台統整並回覆驗收結果 |
| 強茂使用者 | ★ | 1. 依據需求規格文件及實際作業情境進行驗收確認。 </br> 2. 確認系統功能、流程及輸出結果是否符合需求。 |

# Phase 6 — 結案
:::info
結案後，APP 將部署於 **強合智慧** 提供之伺服器環境，後續維運與技術支援作業由強合智慧負責，相關費用將依實際需求及服務範圍另行計價。
:::

### 目的 
於專案完成驗收及正式上線後，針對專案執行成果、交付文件、系統版本及後續維運安排進行結案確認，確保各項工作皆已完成並具備移交條件，作為專案正式結案之依據。

### 階段產出
1. APP 網址。
2. SP 結算：
    - 最終 SP = 開案 SP ± 變更 SP
    - 費用：最終 SP × 單價
3. 窗口聯絡群組解散。

# SP 計費流程摘要
![image](https://hackmd.io/_uploads/BkKYYN73be.png)

### 開案
估算總 SP → 專案費用 = 總 SP × SP 單價

### 執行
SP點數若有增加，
小於10% 以內 IT 裁決，
大於10%由需求單位主管同意後繼續執行

### 驗收
修復錯誤(bug) 不計費（開發方品質責任）

### 結案
按驗收通過的SP 最終結算
