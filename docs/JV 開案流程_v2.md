## 名詞說明
| 名詞 | 說明 |
| -- | -- |
| **Story Point（SP）** | 衡量需求開發工作量的單位，綜合考量複雜度、工時與風險。點數越高代表工作量越大。 |
| **SP 單價** | 每點 SP 對應之費用。專案費用 = 總 SP × SP 單價。 |
| **預估 SP** | 需求訪談後之初步估點。**開案確認前**得依評估結果調整，屬雙方內部作業，**不需Scrum Master簽核**。 |
| **確認 SP** | 經 Phase 3 開案確認（Scrum Master簽核）後之 SP，作為實際扣款基準；此後之增減一律循「設計變更」程序辦理。 |
| **SP 錢包** | 各子公司每年之 SP 配額。所有需求共用此額度，於平台「SP 錢包」查詢餘額。 |
| **設計變更（DC）** | 開案通過後，需求內容出現新增／修改／刪減時，用以正式記錄該變動的機制。 |
| **需求窗口** | 該需求於需求方之對口，負責代表需求方進行確認與簽核。 |
| **需求主管** | 需求窗口之上級主管，若有指派則須一併簽核。 |
| **Scrum Master** | 具開案與 SP 決策權之角色，原則上由該廠最高主管擔任，通常為該廠 IT 最高主管，並由平台依案件所屬廠區或公司別自動指派。 |

# 流程總覽

平台之需求狀態與本文件之階段對應如下：

| # | 階段 | 平台狀態 | 必要文件 | 簽核對象 |
|---|---|---|---|---|
| 1 | 需求確認 | `需求確認` | 會議記錄 | — |
| 2 | PRD 文件確認 | `PRD 文件確認` | PRD 需求規格文件 | 需求窗口＋需求主管<br>（需求主管若有指派） |
| 3 | 開案確認 | `開案確認` | SP 規劃文件 | Scrum Master |
| 4 | 開發 | `開發中` | SDD、APP 交付成果 | 需求窗口＋需求主管<br>（需求主管若有指派）<br>（首次 APP 交付確認） |
| 5 | 驗收 | `驗收中` | BDD、TDD、測試報告 | 需求窗口＋需求主管<br>（需求主管若有指派） |
| 6 | 結案 | `已結案` | — | Scrum Master（僅 SP 有調整時） |

> 上表為主流程階段；下列狀態或附屬流程不列入 6 大主流程：
>
> - `暫緩`、`已取消`、`已駁回` 為專案暫停、不續行或退回時使用之狀態；其中開案前不續行者，以「取消」處理。
> - 「設計變更」為開案後範圍調整流程，適用於 `開發中`、`驗收中`。
> - 「終止開發結案」為開案後提前結束並結算已投入工作量之例外流程，僅適用於 `開發中`、`驗收中`。

## 簽核通則
- 簽核一律於 **JV 需求管理平台** 進行，系統自動通知簽核人並保留完整紀錄。
- 同一關卡的多位簽核人為**併行**關係：誰先簽都可以，**全部同意**才會推進；**任一人退回**即中止該關。
- **需求窗口為必要簽核人；需求主管為選填角色，若有指派則須一併簽核，未指派者不列入待簽核對象。**
- 管理者於特殊情況下可**略過簽核**，惟須填寫原因，紀錄為「管理者略過」並留存於簽核紀錄。
- 該階段若有**尚未完成的設計變更**，階段簽核會被擋住，須先完成設計變更審核。

## 1.1 需求提案
### 目的

## 1.2 需求訪談
### 目的
針對評估後需委由強合智慧開發之需求，由需求窗口、強茂 IT 與強合智慧三方共同參與需求訪談，透過需求窗口說明需求內容、現行作業流程及預期目標，進一步釐清現況流程、深掘作業痛點與使用者樣貌，並確認系統邊界、整合需求及成功 KPI，作為後續需求定義、系統規劃與開發執行之依據。

### 階段產出
1. 需求訪談會議記錄。（平台必要文件）
2. 建立窗口聯絡群組。
3. 指派**需求窗口**（必要）與**需求主管**（選填）。

:::warning
**需求窗口為必要指派項目。** 未指派需求窗口者無法推進至下一階段——後續所有簽核與設計變更確認皆以需求窗口為對象。
:::

| 強合智慧 | ● | 1. 參與需求訪談，了解需求內容與作業情境。 </br> 2. 協助分析痛點、需求可行性與改善方向。 </br> 3. 提出系統設計、整合方式及技術建議。 </br> 4. 協助確認功能範圍、開發重點與可能風險。 </br> 5. 依訪談結果進行後續系統規劃與開發評估。 | 需求訪談會議記錄 |

# Phase 2 — PRD 文件確認

![ChatGPT Image 2026年9月14日 下午02_32_29 (2)](https://hackmd.io/_uploads/S1O2rfBYfl.png)

### 目的
依據需求訪談結果整理並產出**需求規格文件（PRD）**，明確界定本案需求範圍、功能清單、流程規格與優先開發內容，供需求方逐項確認，作為後續開案評估與開發執行之依據。

==**PRD 需求規格文件確認以三次為限（含第一次）。**==

三次內完成確認者，即依既有預估 SP 進入 Phase 3 — 開案確認。

**超過三次時**，由強合智慧**內部評估**後續處理方式（擇一）：

| 處理方式 | 說明 |
| -- | -- |
| **調整預估 SP** | 依實際往返投入之工作量，重新評估本案預估 SP，作為開案確認之基準 |
| **保留至開案後處理** | 超出三次之調整內容不於本階段處理，俟開案後併入評估 |
| **評估不予開發** | 需求持續無法收斂時，得評估不予開發，以「**取消**」結束 |

:::info
**本階段之 SP 仍為「預估 SP」，尚未經開案確認。**
因此上述之 SP 調整屬**內部評估作業，不需Scrum Master簽核**。
Scrum Master之 SP 決策自 **Phase 3 — 開案確認** 起適用；正式開案後之 SP 增減，一律循「設計變更」程序辦理。
:::

> 是否開案之決策，屬 Phase 3 — 開案確認之範疇，詳見該章節。開案前若不續行，應以「取消」處理。

### 階段產出
1. **PRD 需求規格文件**（平台必要文件）——內含需求範圍、功能清單、流程規格與優先開發內容。

:::info
PRD 可記載 P1／P2／P3 等分階段規劃，用於說明整體藍圖；是否納入本次開案，仍以 PRD 與 SP 規劃文件標示之「本次範圍」為準。

本次開案之 SP、費用、交付與驗收僅包含本次範圍；未列入本次範圍之 P2／P3，須另行提案、估算 SP 並重新開案。
:::

### 簽核
> 於 JV 需求管理平台進行簽核。

| 簽核對象 | 說明 |
| -- | -- |
| **需求窗口**（必要） | 確認 PRD 需求規格文件內容符合需求 |
| **需求主管**（若有指派） | 需一併同意 |

- ✅ **確認通過** → 進入 Phase 3 — 開案確認。
- ❌ **退回修改** → 由強合智慧依退回原因調整後重新送簽。

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- |  -- |
| Scrum Master | ○ | 依案件緊急程度評估是否參與。 | |
| 強合智慧 | ★ | 1. 依需求訪談結果整理需求範圍、功能內容與流程規格。 </br> 2. 撰寫 PRD 需求規格文件。 </br> 3. 依需求方回饋修訂 PRD 內容。 </br> 4. 依確認結果評估後續調整方向與開發規劃。 | PRD 需求規格文件 |
| 強茂 IT | ● | 1. 視需要提供內部系統、資料來源與既有流程資訊。 </br> 2. 協助需求窗口與強合智慧之間的需求確認與溝通。 </br> 3. 協助彙整確認回饋，作為後續調整與開發依據。 | |
| 需求窗口／需求主管<br>（需求主管若有指派） | ★ | 1. 確認需求訪談內容與 PRD 需求規格文件是否一致。 </br> 2. 協助確認需求範圍、功能優先順序及規格重點。 </br> 3. 針對 PRD 所載功能與流程提供回饋意見。 </br> 4. **於平台完成本階段簽核。** | 平台簽核紀錄 |

# Phase 3 — 開案確認

![ChatGPT Image 2026年9月14日 下午03_12_30 (1)](https://hackmd.io/_uploads/HyqF0MrtMg.png)

## 3.1 技術可行性評估
### 目的
於開案審核前，由強合智慧依據 PRD 需求規格文件所列之功能需求，主導確認開發範圍、實作邊界與 SP 點數規劃；強茂 IT 視需要提供內部系統、資料來源、權限或既有流程資訊，協助確認評估內容之合理性，作為後續開案審核與資源安排之依據。

### 階段產出
1. **SP 規劃文件**（平台必要文件）。
2. 各階段 SP 點數與時程分配（登錄於平台）。

計算方式：**專案費用 = 總 SP × SP 單價**

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- | -- |
| Scrum Master | — | | |
| 強合智慧 | ★ | 1. 主導會議安排與議題確認。 </br> 2. 依 PRD 需求規格文件評估可承作項目與協作範圍。 </br> 3. 視需要與強茂 IT 確認功能分工、資料來源、權限及實作邊界。 </br> 4. 參與 SP 點數評估與工時規劃討論。 </br> 5. 提供後續開發排程與資源配置建議。 | SP 規劃文件 |

![開發流程v2.1](https://hackmd.io/_uploads/SJUtKUpdfe.png)

| 項目 | 內容 |
| -- | -- |

⚠️ **不會重複認列。** 本項取代原本「進入驗收中」的那 25%——已確認者推進到驗收中時增量為 **0**，全案總認列仍為 100%。未確認連結者，則維持原規則於進入驗收中時認列。

# 設計變更（Design Change）

![ChatGPT Image 2026年9月14日 下午03_15_55 (1)](https://hackmd.io/_uploads/HJs8y7BYMe.png)

### 目的
開案通過、進入開發流程後，若內容出現**新增、修改或刪減**，與已確認之範圍不同，即應循設計變更程序正式記錄。其核心目的是把每一次提出的反饋與修正**留成證據**，作為結案 SP 增減與釐清範圍的依據。

### 何時需要／不需要發起
| | 情境 |
| -- | -- |
| **需要發起** | 1. 需求窗口於開發或驗收過程中提出新需求，或推翻／調整原已確認之內容。</br> 2. 原確認的功能範圍、規格或流程被變動，尤其是會影響 SP 的變動。</br> 3. 討論或測試後達成的共識，需要留下正式紀錄以利日後對齊。 |
| **不需要發起** | 1. 純 bug 修正、不改變原需求範圍的實作細節調整。</br> 2. 小幅畫面、文字或操作細節調整，且不改變原需求範圍與功能邏輯者，不另計 SP。</br> 3. 仍在「需求確認」階段、需求本身還在討論成形時——直接修改需求即可。</br> 4. PRD 中列為 P2／P3 等後續階段之需求，未納入本次開案範圍者，應另行開案，不以原案設計變更處理。 |

### 可發起階段
`開發中`、`驗收中`

:::warning
**已結案後不可再發起設計變更。** 結案時 SP 已依設計變更紀錄完成結算；若 SP 有調整，亦已經 Scrum Master 核准。此時再開變更會使結算基準與紀錄不一致。
:::

### 審核關卡（兩關）

**第一關 · 設計變更確認**

| 簽核對象 | 說明 |
| -- | -- |
| **Scrum Master** | **一律參與，不論是否影響 SP**；由平台依案件所屬廠區或公司別自動指派 |
| **需求窗口** | 預設為專案需求窗口，發起時可手動改選 |

- 兩方為**併行**關係，誰先簽都可以，不分先後。
- 本關僅裁決「**准不准開立此變更**」，**不需**逐條勾選檢查清單。
- **任一方駁回即中止**，不會進入第二關。

**第二關 · 逐條確認**

| 簽核對象 | 說明 |
| -- | -- |
| **需求窗口**（必要） | 沿用第一關指定之窗口 |
| **需求主管**（若有指派） | 需一併同意 |

- 逐條檢視檢查清單，每一條可標記 **確認 / 疑慮 / 問題** 並補充說明。
- **全部項目皆標記為「確認」** 才能通過；有疑慮或問題請退回並說明。
- 本關通過後，整筆設計變更才算完成。

:::info
需求窗口在兩關都需要簽核，但兩者意義不同：**第一關是「准不准開」，第二關是「內容對不對」**，並非重複簽核。
:::

### 修訂與退回
- 被退回後，開發端可修訂內容並提出**新版本**（v2、v3…）。
- 新版本若**第一關先前已通過**，會**直接進入第二關**，不必重新裁決是否開立；若當初是卡在第一關，才需重走一次。
- 各版本之審核結果皆完整保留，可於平台逐版對照。

### 重要說明
- 設計變更期間，階段狀態顯示為「階段名稱 - 設計變更」（例如：驗收中 - 設計變更）。
- 設計變更通過後**不會**自動改變需求狀態或 SP；但**該階段的簽核會被擋住**，直到此階段的設計變更全部通過或撤銷。
- 相關 SP 增減一律於**結案階段**結算，**不得於中途逕自修改已確認的 SP**。
- 尚未確認的設計變更，管理者可編輯或刪除；**已通過者不可再編輯**，以保全紀錄。

# Phase 6 — 結案

![ChatGPT Image 2026年9月10日 下午01_08_00 (1)](https://hackmd.io/_uploads/BJntj2JYGg.png)

### 目的
於專案完成驗收後，針對專案執行成果、交付文件、系統版本及後續維運安排進行結案資料確認與結果彙整，確保各項工作皆已完成並具備移交條件，作為專案正式結案之依據。

### 結案作業程序
於平台進行結案時，依序確認下列事項：

1. **簽核確認** — 檢視驗收階段簽核狀態；如仍有待簽核，須明確選擇是否略過並填寫原因。
2. **文件確認** — 檢視各階段必要文件是否齊備。
3. **SP 調整** — 系統依已通過之設計變更**自動推算**結案 SP。
4. **關聯設計變更** — 勾選造成本次 SP 調整之設計變更（系統已預先勾選）。
5. **確認結案** — 送出。

### SP 結算規則

==**結案 SP ＝ 專案原始 SP ＋ 所有「已通過」設計變更之增減總和**==

| 規則 | 說明 |
| -- | -- |
| **只認最終通過的版本** | 例如某設計變更提出 +2 被退回、改為 +1 才通過，僅計 **+1**。 |
| **駁回者完全不計** | 整筆被駁回或撤銷的設計變更，**不計入**結算。 |
| **系統自動帶入** | 金額由平台推算並鎖定，**管理者不需自行計算或填寫**。 |
| **例外覆寫** | 特殊情況得手動覆寫，惟**必須填寫原因**，並記入操作紀錄供事後查核。 |

### 結案簽核
> 於 JV 需求管理平台進行簽核。

**SP 有調整時，必須經Scrum Master簽核才能完成結案。**

| 項目 | 說明 |
| -- | -- |
| 簽核對象 | **Scrum Master** |
| 送出後狀態 | 顯示為「**結案簽核中**」，需求**尚未結案** |
| 期間限制 | **不可變更階段**，亦**不可重複送出**結案申請 |
| ✅ 同意 | 實際套用 SP 調整、更新 SP 錢包並完成結案 |
| ❌ 退回 | 維持原階段，可修正後重送；如需修改內容，須先撤回該結案簽核 |

> SP 未調整者，不需Scrum Master簽核，可直接完成結案。

### 階段產出
1. APP 網址。
2. SP 結算紀錄（含關聯之設計變更）。
3. 窗口聯絡群組解散。

### 部署順序
開發與驗收期間，APP 原則上部署於測試區供需求方確認；專案結案後，再移轉至正式區提供正式使用。測試區與正式區之網址規劃，原則上以 JV 相關網域統一管理。

:::info
結案後，APP 將部署於 **強合智慧** 提供之伺服器環境，後續維運與技術支援作業由強合智慧負責，相關費用將依實際需求及服務範圍另行計價。
:::

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- | -- |
| Scrum Master | ★ | 1. 僅於結案 SP 有調整時進行簽核。 </br> 2. 審核結案 SP 調整；同意後方完成結案。 | 平台簽核紀錄 |
| 強合智慧 | ★ | 依結案結果完成專案收尾與正式結束作業。 | 1. APP 網址 </br> 2. SP 結算紀錄（含關聯之設計變更） |
| 強茂 IT | ● | 1. 檢視專案結案結果與 SP 結算內容。 </br> 2. 如有內部作業需要，協助轉知相關單位。 | |
| 需求窗口／需求主管<br>（需求主管若有指派） | ● | 1. 接收專案結案通知。 </br> 2. 檢視系統已完成驗收、上線及交付結果。 | |

# 專案終止、取消、暫緩

![ChatGPT Image 2026年9月14日 下午03_20_43 (1)](https://hackmd.io/_uploads/By0ulXHKfl.png)

## 定義：暫緩、取消、終止

三者最常被混用，但**對 SP 的處置**與**專案是否結束**完全不同：

| | **暫緩** | **取消** | **終止開發結案** |
| -- | -- | -- | -- |
| **意義** | 因故先停下，將來可能重啟 | 需求不再成立 | 就已投入部分結算，專案結束 |
| **SP 處置** | ==**押住不動**==（HOLD 在暫緩前的階段） | ==**全額釋放**==、不計費 | ==**結算於選定落點**==（50%／75%／100%） |
| **專案是否結束** | 否，仍在進行中 | 否，需求保留可再啟動 | ==**是，結束後不再重開**== |
| **未來重啟** | 直接解除暫緩，接續原進度 | 可再啟動，SP 另行評估 | **不重啟**；如仍要做，須另開新需求 |
| **Scrum Master 簽核** | 不需 | 不需 | ==**必須**== |
| **平台狀態** | `暫緩` | `已取消` | `終止簽核中` → `已終止` |

---

以下說明**取消**與**終止開發結案**兩種提前結束的作業程序。開案前不續行者，以「取消」處理；開案後若已投入實質工作量且雙方同意結算，才適用「終止開發結案」。

:::info
取消或終止開發結案前，應先由強合智慧與強茂相關窗口完成事前溝通，確認原因、目前進度與 SP 處理方式後，再於平台執行對應作業並留存紀錄。
:::

## 一、取消需求（不計費）

適用於開案前需求方主動撤回、需求不再成立，或雙方未形成開案共識之情形。

| 項目 | 說明 |
| -- | -- |
| 發起方式 | 由管理者於平台將需求標記為「**已取消**」並填寫原因 |
| 是否需簽核 | **不需**Scrum Master簽核 |
| SP 處理 | **全額釋放**，不計費 |
| 紀錄 | 需求保留於系統中，可日後重新啟動 |

## 二、終止開發結案（需Scrum Master簽核，依比例結算）

適用於已投入實質工作量、雙方同意就該部分結算並正式結束專案之情形。

| 項目 | 說明 |
| -- | -- |
| 發起方式 | 由管理者於平台發起「**Scrum Master 代簽**」並選擇**結算落點** |
| 可發起階段 | 僅限 `開發中`、`驗收中`。 |
| 簽核對象 | **Scrum Master** |
| 簽核期間狀態 | 顯示為「**終止簽核中**」，需求尚未結束 |
| Scrum Master同意後 | 依所選落點比例結算 SP，需求狀態轉為結案並顯示為「**已終止**」；其餘待簽核自動略過 |

### 結算比例
終止開發結案不是退回前一流程，也不是重新判定專案階段；而是在專案提前停止時，依已通過的 SP 認列節點結算，並將案件關閉為「已終止」。

| 終止結算落點 | 認列比例 | 適用情境 |
| -- | -- | -- |
| 開案確認已通過 | **50%** | 已開案並進入開發，但尚未完成首次 APP 交付確認，也尚未進入驗收。 |
| 首次 APP 交付確認／驗收中 | **75%** | 已完成首次 APP 交付確認，或已進入驗收階段。 |
| 實質完成 | **100%** | 功能實質完成並已達可結案狀態，僅因程序或雙方決議以終止方式收尾。 |

:::warning
**終止開發結案僅適用於開案後。** 若需求仍停留在 PRD 文件確認或開案確認階段，應以「**取消**」方式結束，SP 全額釋放、不計費。
:::

# SP 計費與認列

![ChatGPT Image 2026年9月14日 下午03_23_45 (1)](https://hackmd.io/_uploads/BygVZQBtMl.png)


### 計費基準
**專案費用 = 最終 SP × SP 單價**

### 分階段認列機制

SP 分三段認列，==**均於該關卡「通過後」才起算**==，而非開案即全額扣除：

| 觸發時點（通過後） | 本次認列 | 累計 | 對應平台狀態 |
| -- | -- | -- | -- |
| **① 開案確認 通過** | **50%** | 50% | 進入「開發中」 |
| **② 首次 APP 交付確認** | **25%** | 75% | 開發中（首次 APP 交付經確認）<br>或 進入「驗收中」 |
| **③ 結案 完成** | **25%** | 100% | 「已結案」 |

**其他情形**
- 需求**暫緩**或**駁回**時，依其進入該狀態前已通過的關卡計算認列。
- 需求**取消**時，**全額釋放**已認列之 SP。
- SP 錢包之可用餘額 ＝ 年度配額 − 已認列 SP。

### 各階段之 SP 處理
| 階段 | 處理方式 |
| -- | -- |
| **開案** | 估算總 SP，作為專案基準。 |
| **執行** | SP 如有增減，一律循**設計變更**程序辦理，經第一關（Scrum Master＋需求窗口）與第二關（需求窗口／需求主管〔若有指派〕逐條確認）通過後生效。 |
| **交付** | 需求方確認首次 APP 交付時，認列第二段的 25%（每案僅一次）；未確認者則於進入「驗收中」時認列，兩者擇一、不重複。 |
| **驗收** | 修復錯誤（bug）**不計費**，屬開發方品質責任。 |
| **結案** | 依已通過之設計變更自動結算；無 SP 調整可直接結案，有 SP 調整才送 **Scrum Master簽核**。 |
| **提前終止** | 循「終止開發結案」程序，經**Scrum Master簽核**依落點比例（50%／75%／100%）結算；單純取消則全額釋放、不計費。 |
