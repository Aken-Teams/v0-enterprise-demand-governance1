## 名詞說明
| 名詞 | 說明 |
| -- | -- |
| **Story Point（SP）** | 衡量需求開發工作量的單位，綜合考量複雜度、工時與風險。點數越高代表工作量越大。 |
| **SP 單價** | 每點 SP 對應之費用。專案費用 = 總 SP × SP 單價。 |
| **預估 SP** | 需求訪談後之初步估點。**開案確認前**得依評估結果調整，屬雙方內部作業，**不需Scrum Master簽核**。 |
| **確認 SP** | 經 Phase 3 開案確認（Scrum Master簽核）後之 SP，作為實際扣款基準；此後之增減一律循「設計變更」程序辦理。 |
| **SP 錢包** | 各子公司每年之 SP 配額。所有需求共用此額度，於平台「SP 錢包」查詢餘額。 |
| **設計變更（DC）** | 需求通過需求確認、進入開發流程後，內容出現新增／修改／刪減時，用以正式記錄該變動的機制。 |
| **需求窗口** | 該需求於需求方之對口，負責代表需求方進行確認與簽核。 |
| **需求主管** | 需求窗口之上級主管，若有指派則須一併簽核。 |
| **Scrum Master** | 具開案與 SP 決策權之角色，依「一間公司一位」之優先序自動指派。*（註：JV 需求管理平台之介面將此角色標示為「董事會」，兩者為同一角色。）* |

## 角色說明
| **角色** | **說明** |
| -- | -- |
| **Scrum Master** | 促進 Scrum 流程的實施，移除團隊障礙，並確保團隊高效運行；並負責開案最終決策、設計變更開立之裁決，以及結案 SP 調整之核准。|
| **強合智慧** | 負責需求分析、系統規劃、設計開發、測試修正、系統部署及後續維運支援等相關技術執行作業。|

# 流程總覽

平台之需求狀態與本文件之階段對應如下：

| # | 階段 | 平台狀態 | 必要文件 | 簽核對象 |
|---|---|---|---|---|
| 1 | 需求確認 | `需求確認` | 會議記錄 | — |
| 2 | MVP 架構確認 | `MVP 架構確認` | PRD 需求規格文件 | 需求窗口＋需求主管 |
| 3 | 開案確認 | `開案確認` | SP 規劃文件 | Scrum Master |
| 4 | 開發 | `開發中` | SDD、APP 交付成果、GitHub 連結 | 需求窗口＋需求主管<br>（首次 APP 交付確認） |
| 5 | 驗收 | `驗收中` | BDD、TDD、測試報告 | 需求窗口＋需求主管 |
| 6 | 結案 | `已結案` | — | Scrum Master（僅 SP 有調整時） |

> 另有 `暫緩`、`已取消`、`已駁回` 等狀態，供專案中止或擱置時使用；SP 之認列依實際所在階段計算。
> **GitHub 連結**為平台必要文件（未上傳無法推進階段），惟基於原始碼機密性，**不對需求方開放檢視**。

## 簽核通則
- 簽核一律於 **JV 需求管理平台** 進行，系統自動通知簽核人並保留完整紀錄。
- 同一關卡的多位簽核人為**併行**關係：誰先簽都可以，**全部同意**才會推進；**任一人退回**即中止該關。
- 管理者於特殊情況下可**略過簽核**，惟須填寫原因，紀錄為「管理者略過」並留存於簽核紀錄。
- 該階段若有**尚未結案的設計變更**，階段簽核會被擋住，須先完成設計變更審核。

# Phase 1 — 需求確認

![需求提出V2](https://hackmd.io/_uploads/B1qEhH3_fe.png)

## 1.1 需求提案
### 目的
使用者提出需求後，由強茂 IT 先進行初步確認與評估，優先判斷是否可透過既有系統調整或功能擴充方式處理；若現有系統無法支援，再評估是否需開發新系統，並依需求規模及資源配置，決定由強茂 IT 自行開發或委由強合智慧協助開發。

==**若由強茂 IT 自行開發，則不適用此開案流程。**==

### 階段產出
1. 需求提案會議記錄。
2. 紀錄於強茂需求清單中。

> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- | -- |
| Scrum Master | ○ | 依案件緊急程度評估是否參與。 | |
| 強合智慧 | — | | |
| 強茂 IT | ● | 1. 與使用者進行需求初步訪談與確認。 </br> 2. 釐清需求範圍、功能內容及可行性。 </br> 3. 評估開發規模、所需資源與時程。 </br> 4. 判斷由強茂內部自行開發或委由強合智慧開發。 | 1. 需求提案會議記錄 </br> 2. 紀錄於強茂需求清單中 |

## 1.2 需求訪談
### 目的
針對評估後需委由強合智慧開發之需求，由使用者、強茂 IT 與強合智慧三方共同參與需求訪談，透過使用者說明需求內容、現行作業流程及預期目標，進一步釐清現況流程、深掘作業痛點與使用者樣貌，並確認系統邊界、整合需求及成功 KPI，作為後續需求定義、系統規劃與開發執行之依據。

### 階段產出
1. 需求訪談會議記錄。（平台必要文件）
2. 建立窗口聯絡群組。
3. 指派**需求窗口**（必要）與**需求主管**（選填）。

:::warning
**需求窗口為必要指派項目。** 未指派需求窗口者無法推進至下一階段——後續所有簽核與設計變更確認皆以需求窗口為對象。
:::

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- | -- |
| Scrum Master | ○ | | |
| 強合智慧 | ● | 1. 參與需求訪談，了解需求內容與作業情境。 </br> 2. 協助分析痛點、需求可行性與改善方向。 </br> 3. 提出系統設計、整合方式及技術建議。 </br> 4. 協助確認功能範圍、開發重點與可能風險。 </br> 5. 依訪談結果進行後續系統規劃與開發評估。 | 需求訪談會議記錄 |
| 強茂 IT | ★ | 1. 主導需求訪談安排與三方溝通協調。 </br> 2. 協助釐清需求內容、現況流程及業務邏輯。 </br> 3. 確認需求範圍、系統邊界與整合需求。 </br> 4. 與各方共同定義成功 KPI 與開發方向。 </br> 5. 彙整訪談結論，作為後續評估與執行依據。 | 建立窗口聯絡群組 |

# Phase 2 — MVP 架構確認

![MVP流程V2](https://hackmd.io/_uploads/SJRs7U2OGg.png)

### 目的
依據需求訪談結果定義最小可行產品（MVP）範圍，明確界定本階段優先開發之功能與系統邊界，並據以產出需求規格文件（PRD）及初步系統網址，供使用者進行初步介面與流程驗證，作為後續系統調整與開發之依據。

==**MVP 階段之 PRD 與 MVP 內容確認以三次為限（含第一次）。**==

三次內完成確認者，即依既有預估 SP 進入 Phase 3 — 開案確認。

**超過三次時**，由強合智慧**內部評估**後續處理方式（擇一）：

| 處理方式 | 說明 |
| -- | -- |
| **調整預估 SP** | 依實際往返投入之工作量，重新評估本案預估 SP，作為開案確認之基準 |
| **保留至開案後處理** | 超出三次之調整內容不於本階段處理，俟開案後併入評估 |
| **評估不予開發** | 需求持續無法收斂時，得評估不予開發，以「**取消**」結束 |

:::info
**本階段之 SP 仍為「預估 SP」，尚未經開案確認。**
因此上述之 SP 調整屬**內部評估作業，不需Scrum Master簽核**。
Scrum Master之 SP 決策自 **Phase 3 — 開案確認** 起適用；正式開案後之 SP 增減，一律循「設計變更」程序辦理。
:::

> 是否開案、是否終止結算等決策，屬 Phase 3 — 開案確認之範疇，詳見該章節。

### 階段產出
1. MVP 範圍定義書。
2. **PRD 需求規格文件**（平台必要文件）。
3. MVP 初步系統網址。

### 簽核
> 於 JV 需求管理平台進行簽核。

| 簽核對象 | 說明 |
| -- | -- |
| **需求窗口**（必要） | 確認 PRD 與 MVP 範圍符合需求 |
| **需求主管**（若有指派） | 需一併同意 |

- ✅ **確認通過** → 進入 Phase 3 — 開案確認。
- ❌ **退回修改** → 由強合智慧依退回原因調整後重新送簽。

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- |  -- |
| Scrum Master | ○ | 依案件緊急程度評估是否參與。 | |
| 強合智慧 | ● | 1. 依需求訪談結果規劃 MVP 架構與功能內容。 </br> 2. 撰寫 MVP 範圍定義書及 PRD 需求規格文件。 </br> 3. 建置 MVP 初步系統網址供使用者驗證。 </br> 4. 依驗證結果評估後續調整方向與開發規劃。 | 1. MVP 範圍定義書 </br> 2. PRD 需求規格文件 </br> 3. MVP 初步系統網址 |
| 強茂 IT | ★ | 1. 協調使用者與強合智慧之間的需求確認與溝通。 </br> 2. 審視 PRD 文件及 MVP 內容是否符合需求方向。 </br> 3. 彙整驗證回饋，作為後續調整與開發依據。 | |
| 強茂使用者 | ★ | 1. 確認需求訪談內容與 PRD 需求規格文件是否一致。 </br> 2. 協助確認 MVP 範圍、功能優先順序及驗證重點。 </br> 3. 針對 MVP 初步系統介面與流程提供回饋意見。 </br> 4. **於平台完成本階段簽核。** | 平台簽核紀錄 |

# Phase 3 — 開案確認

![開案流程V2](https://hackmd.io/_uploads/ry6mLIh_fl.png)

## 3.1 技術可行性評估
### 目的
於開案會議前，由雙方 IT 共同召開會議，依據 PRD 需求規格文件所列之功能需求，確認開發範圍與合作分工，並針對可協作項目進行討論，評估各項功能之 SP 點數歸屬，作為後續開發規劃與資源安排之依據。

### 階段產出
1. **SP 規劃文件**（平台必要文件）。
2. 各階段 SP 點數與時程分配（登錄於平台）。

計算方式：**專案費用 = 總 SP × SP 單價**

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- | -- |
| Scrum Master | ○ | 依案件緊急程度評估是否參與。 | |
| 強合智慧 | ★ | 1. 主導會議安排與議題確認。 </br> 2. 依 PRD 需求規格文件評估可承作項目與協作範圍。 </br> 3. 與強茂 IT 共同討論功能分工及實作邊界。 </br> 4. 參與 SP 點數評估與工時規劃討論。 </br> 5. 提供後續開發排程與資源配置建議。 | SP 規劃文件 |
| 強茂 IT | ● | 1. 依 PRD 內容提出可協作範圍與內部分工建議。 </br> 2. 與強合智慧共同確認開發範圍及 SP 點數歸屬。 </br> 3. 彙整會議結論，作為後續開案與執行依據。 | |
| 強茂使用者 | — |  | |

## 3.2 開案會議與審核
### 目的
由強茂 IT 召開會議，針對專案開發內容向需求單位（含主管）說明本案開發方向、收費方式及執行分工，並確認需求內容與專案範疇；<span style="background-color:#CE0000"><font color="#FFFFFF"> 另同步建立共識：如後續新增或調整需求，須循「設計變更」程序辦理，並依影響範圍評估增加之 SP 點數與時程。 </font></span>

### 階段產出
1. 專案開案單（檢附需求方主管簽核證明）。
2. BPM PJM02 資訊服務申請單。
    - 審核項目：需求明確性、技術可行性、SP 合理性、預算、時程。

### 簽核
> 於 JV 需求管理平台進行簽核。

| 簽核對象 | 說明 |
| -- | -- |
| **Scrum Master** | 為本階段之最終決策者 |

- ✅ **確認通過** → 進入 Phase 4 — 開發，進行完整 APP 開發；此時之 SP 成為「**確認 SP**」，後續增減須循設計變更程序。
- ❌ **退回修改** → 依退回原因修正後重新送簽。
- ⛔ **不予開案** → 依已投入之工作量分兩種處理：
  - 未投入實質工作量，或雙方無結算共識 → 以「**取消**」結束，**SP 全額釋放、不計費**。
  - 已投入實質工作量且雙方同意結算 → 循「**終止開發結案**」程序辦理，經**Scrum Master簽核**確認結算比例後結算（詳見「專案終止與取消」章節）。

:::warning
**SP 之酌收必須經「終止開發結案」程序並取得Scrum Master簽核**，並非因「未開案」即自動計費。
需求方僅係取消需求、雙方未進行終止結算者，不收取 SP 點數。
:::

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- | -- |
| Scrum Master | ★ | 1. 統整專案評估資訊。 </br> 2. 於平台進行開案簽核，為是否開案之最終決策者。 | 平台簽核紀錄 |
| 強合智慧 | ○ | 1. 提供專案開發內容、費用估算及時程規劃。 </br> 2. 配合審核與簽核流程，補充專案相關說明。 </br> 3. 依核定結果安排後續開發資源與執行計畫。 | |
| 強茂 IT | ★ | 1. 說明技術可行性評估結果，供需求單位主管進行開案決策。 </br> 2. 協調相關單位進行開案審核與簽核作業。 </br> 3. 確認簽核結果，作為後續專案啟動依據。 | |
| 強茂使用者 </br> （含主管） | ● | 1. 確認開發內容是否符合業務需求與預期目標。 </br> 2. 協助確認專案時程是否符合實際作業需求。 </br> 3. 進行需求方主管簽核，確認專案啟動共識。 | 1. 需求主管簽核佐證 </br> 2. 確認開案則開立 M02 |

# Phase 4 — 開發

![JV開發](https://hackmd.io/_uploads/BkITKLnuMe.png)

### 目的
依據 PRD 需求規格文件及每次使用者測試回饋結果，進行系統迭代開發與持續交付，並視專案需求不定期召開討論會議，針對功能調整、需求變更與實作方式進行確認，以確保開發內容符合需求方向與專案目標。

:::danger
⚠️ **注意：**
強合智慧完成 APP 交付或程式修正後，**需求單位應於 10 個工作天內完成確認並回覆**；如逾期未回覆，則該專案將予以暫停，並由開發團隊優先處理其他專案需求，原專案則順延辦理。
:::

### 階段產出
1. 衝刺待辦清單（Sprint Backlog）。
2. **SDD 系統設計文件**（平台必要文件）。
3. **APP 交付成果**（平台必要文件）。

### 首次 APP 交付確認

強合智慧交出**第一個可供試用的 APP 連結**時，平台自動送出確認給需求方。

| 項目 | 內容 |
| -- | -- |
| **確認人** | 需求窗口（必要）＋ 需求主管（若有指派），兩人皆確認後生效 |
| **確認前** | 需求方==**看不到該連結**==，僅顯示「APP 交付連結尚未開放」 |
| **確認後** | 連結立即開放，並==認列 **25%** SP（累計 50% → **75%**）== |
| **次數** | ==**每案僅一次**==；之後更新或重新上傳連結皆直接顯示，不再請求確認 |
| **性質** | 屬**簽收**，不提供退回；對內容有意見請循設計變更或驗收程序反映 |
| **紀錄** | 平台「簽核紀錄」項目名稱為「**首次 APP 交付確認**」 |

:::warning
⚠️ **不會重複認列。** 本項取代原本「進入驗收中」的那 25%——已確認者推進到驗收中時增量為 **0**，全案總認列仍為 100%。未確認連結者，則維持原規則於進入驗收中時認列。
:::

> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- | -- |
| Scrum Master | — | | |
| 強合智慧 | ★ | 1. 依 PRD 與回饋結果規劃 Sprint Backlog 與開發內容。 </br> 2. 撰寫與更新 SDD 系統設計文件。 </br> 3. 執行系統開發、功能調整與階段性交付。 </br> 4. 參與討論會議。 </br> 5. **需求範圍如有變動，提出設計變更。** | 1. 衝刺待辦清單 </br> 2. SDD 系統設計文件</br> 3. APP 交付成果 </br> 4. GitHub 連結 |
| 強茂 IT | ● | 1. 彙整使用者測試回饋與需求調整事項。  </br> 2. 協調使用者與強合智慧確認 Sprint 開發內容。  </br> 3. 追蹤開發進度、確認交付項目與需求一致性。 </br> 4. 召開或安排討論會議，協助釐清需求與調整方向。 </br> 5. **確認首次 APP 交付（認列 25% SP，每案一次）。** | |

# 設計變更（Design Change）

![設計變更V2](https://hackmd.io/_uploads/SJ9UwI2ufl.png)

### 目的
需求通過「需求確認」、進入開發流程之後，若內容出現**新增、修改或刪減**，與當初確認之範圍不同，即應循設計變更程序正式記錄。其核心目的是把每一次提出的反饋與修正**留成證據**，作為結案時 SP 增減與釐清範圍的依據。

### 何時需要／不需要發起
| | 情境 |
| -- | -- |
| **需要發起** | 1. 使用者於開發或驗收過程中提出新需求，或推翻／調整原已確認之內容。</br> 2. 原確認的功能範圍、規格或流程被變動，尤其是會影響 SP 的變動。</br> 3. 討論或測試後達成的共識，需要留下正式紀錄以利日後對齊。 |
| **不需要發起** | 1. 純 bug 修正、不改變原需求範圍的實作細節調整。</br> 2. 仍在「需求確認」階段、需求本身還在討論成形時——直接修改需求即可。 |

### 可發起階段
`開案確認`、`開發中`、`驗收中`

:::warning
**已結案後不可再發起設計變更。** 結案時 SP 已依設計變更紀錄完成結算並經Scrum Master核准，此時再開變更會使結算基準與紀錄不一致。
:::

### 審核關卡（兩關）

**第一關 · 設計變更確認**

| 簽核對象 | 說明 |
| -- | -- |
| **Scrum Master** | **一律參與，不論是否影響 SP**；依「一間公司一位」之優先序自動指派 |
| **需求窗口** | 預設為專案需求窗口，發起時可手動改選 |

- 兩方為**併行**關係，誰先簽都可以，不分先後。
- 本關僅裁決「**准不准開立此變更**」，**不需**逐條勾選檢查清單。
- **任一方駁回即中止**，不會進入第二關。

**第二關 · 逐條確認**

| 簽核對象 | 說明 |
| -- | -- |
| **需求窗口**（必要） | 沿用第一關指定之窗口 |
| **需求主管**（若有指派） | 需一併同意 |

- 逐條檢視檢查清單，每一條可標記 **確認 / 疑慮 / 問題** 並補充說明。
- **全部項目皆標記為「確認」** 才能通過；有疑慮或問題請退回並說明。
- 本關通過後，整筆設計變更才算完成。

:::info
需求窗口在兩關都需要簽核，但兩者意義不同：**第一關是「准不准開」，第二關是「內容對不對」**，並非重複簽核。
:::

### 修訂與退回
- 被退回後，開發端可修訂內容並提出**新版本**（v2、v3…）。
- 新版本若**第一關先前已通過**，會**直接進入第二關**，不必重新裁決是否開立；若當初是卡在第一關，才需重走一次。
- 各版本之審核結果皆完整保留，可於平台逐版對照。

### 重要說明
- 設計變更期間，階段狀態顯示為「階段名稱 - 設計變更」（例如：驗收中 - 設計變更）。
- 設計變更通過後**不會**自動改變需求狀態或 SP；但**該階段的簽核會被擋住**，直到此階段的設計變更全部通過或撤銷。
- 相關 SP 增減一律於**結案階段**結算，**不得於中途逕自修改已確認的 SP**。
- 尚未確認的設計變更，管理者可編輯或刪除；**已通過者不可再編輯**，以保全紀錄。

![驗收流程V2](https://hackmd.io/_uploads/r1F2dI3OMx.png)

### 目的
由使用者透過驗收作業確認系統開發成果是否符合需求規格文件、業務流程及使用需求，並就功能完整性、操作正確性與交付內容進行檢核，作為系統上線、結案之依據。

### 階段產出
1. **BDD 行為驅動開發文件**（平台必要文件）。
2. **TDD 測試驅動開發文件**（平台必要文件）。
3. **測試報告**（平台必要文件）。
4. （選填）資安報告、資安修正報告、操作手冊。

# Phase 6 — 結案

![結案 V2](https://hackmd.io/_uploads/rkzOK82_Gl.png)

### 目的
於專案完成驗收及正式上線後，針對專案執行成果、交付文件、系統版本及後續維運安排進行結案確認，確保各項工作皆已完成並具備移交條件，作為專案正式結案之依據。

### 結案作業程序
於平台進行結案時，依序確認下列事項：

1. **簽核確認** — 檢視驗收階段簽核狀態；如仍有待簽核，須明確選擇是否略過並填寫原因。
2. **文件確認** — 檢視各階段必要文件是否齊備。
3. **SP 調整** — 系統依已通過之設計變更**自動推算**結案 SP。
4. **關聯設計變更** — 勾選造成本次 SP 調整之設計變更（系統已預先勾選）。
5. **確認結案** — 送出。

### SP 結算規則

==**結案 SP ＝ 專案原始 SP ＋ 所有「已通過」設計變更之增減總和**==

| 規則 | 說明 |
| -- | -- |
| **只認最終通過的版本** | 例如某設計變更提出 +2 被退回、改為 +1 才通過，僅計 **+1**。 |
| **駁回者完全不計** | 整筆被駁回或撤銷的設計變更，**不計入**結算。 |
| **系統自動帶入** | 金額由平台推算並鎖定，**管理者不需自行計算或填寫**。 |
| **例外覆寫** | 特殊情況得手動覆寫，惟**必須填寫原因**，並記入操作紀錄供事後查核。 |

### 結案簽核
> 於 JV 需求管理平台進行簽核。

**SP 有調整時，必須經Scrum Master簽核才能完成結案。**

| 項目 | 說明 |
| -- | -- |
| 簽核對象 | **Scrum Master** |
| 送出後狀態 | 顯示為「**結案簽核中**」，需求**尚未結案** |
| 期間限制 | **不可變更階段**，亦**不可重複送出**結案申請 |
| ✅ 同意 | 實際套用 SP 調整、更新 SP 錢包並完成結案 |
| ❌ 退回 | 維持原階段，可修正後重送；如需修改內容，須先撤回該結案簽核 |

> SP 未調整者，不需Scrum Master簽核，可直接完成結案。

### 階段產出
1. APP 網址。
2. SP 結算紀錄（含關聯之設計變更）。
3. 窗口聯絡群組解散。

:::info
結案後，APP 將部署於 **強合智慧** 提供之伺服器環境，後續維運與技術支援作業由強合智慧負責，相關費用將依實際需求及服務範圍另行計價。
:::

### 角色分工
> 符號說明：`★ 主導`、`● 參與`、`○ 列席`、`— 不參與`

| 角色 | 符號 | 說明 | 階段產出 |
| -- | -- | -- | -- |
| Scrum Master | ★ | 1. 協調使用者與強合智慧完成結案確認作業。 </br> 2. 審核結案 SP 調整；同意後方完成結案。 | 平台簽核紀錄 |
| 強合智慧 | ★ | 依結案結果完成專案收尾與正式結束作業。 | 交付文件 |
| 強茂 IT | ● | 1. 作為專案結案之內部窗口，完成結案程序。 </br> 2. 於平台發起結案並確認 SP 結算內容。 | 結案 SP 送簽 |
| 強茂使用者 | ● | 1. 確認系統已完成驗收、上線及實際使用需求。 </br> 2. 確認交付成果符合業務需求與專案目標。 | |

# 專案終止與取消

![專案終止](https://hackmd.io/_uploads/B1W_9L2Oze.png)

## 定義：暫緩、取消、終止

三者最常被混用，但**對 SP 的處置**與**專案是否結束**完全不同：

| | **暫緩** | **取消** | **終止開發結案** |
| -- | -- | -- | -- |
| **意義** | 因故先停下，將來可能重啟 | 需求不再成立 | 就已投入部分結算，專案結束 |
| **SP 處置** | ==**押住不動**==（HOLD 在暫緩前的階段） | ==**全額釋放**==、不計費 | ==**結算於選定落點**==（50%／75%／100%） |
| **專案是否結束** | 否，仍在進行中 | 否，需求保留可再啟動 | ==**是，結束後不再重開**== |
| **未來重啟** | 直接解除暫緩，接續原進度 | 可再啟動，SP 另行評估 | **不重啟**；如仍要做，須另開新需求 |
| **Scrum Master 簽核** | 不需 | 不需 | ==**必須**== |
| **平台狀態** | `暫緩` | `已取消` | `終止簽核中` → `已終止` |

:::warning
**暫緩中的需求不能直接送出終止開發結案。**
兩者意義相反——暫緩是把 SP 押在原地等待重啟，終止是結算後結束專案。
如確定不再進行，請**先解除暫緩**讓需求回到實際階段，再發起終止開發結案。
（平台亦會擋下暫緩狀態的「專案 Master 代簽」。）
:::

---

以下說明**取消**與**終止開發結案**兩種提前結束的作業程序。兩者的差別在於「有沒有已投入而需計費的工作量」，不在於專案有沒有開案。

## 一、取消需求（不計費）

適用於需求方主動撤回、需求不再成立，且雙方未就已投入工作量進行結算之情形。

| 項目 | 說明 |
| -- | -- |
| 發起方式 | 由管理者於平台將需求標記為「**已取消**」並填寫原因 |
| 是否需簽核 | **不需**Scrum Master簽核 |
| SP 處理 | **全額釋放**，不論取消前進行到哪一階段 |
| 紀錄 | 需求保留於系統中，可日後重新啟動 |

## 二、終止開發結案（需Scrum Master簽核，依比例結算）

適用於已投入實質工作量、雙方同意就該部分結算並正式結束專案之情形。

| 項目 | 說明 |
| -- | -- |
| 發起方式 | 由管理者於平台發起「**專案 Master 代簽**」並選擇**結算落點** |
| 可發起階段 | 僅限 `MVP 架構確認`、`開案確認`、`開發中`、`驗收中` 四個階段。 |
| 簽核對象 | **Scrum Master**（依「一間公司一位」之優先序自動指派） |
| 簽核期間狀態 | 顯示為「**終止簽核中**」，需求尚未結束 |
| Scrum Master同意後 | 依所選落點比例結算 SP，需求狀態轉為結案並顯示為「**已終止**」；其餘待簽核自動略過 |

### 結算比例
結算落點對應之 SP 認列比例如下，且**不得低於需求目前所在階段之比例**：

| 結算落點 | 認列比例 | 適用情境 |
| -- | -- | -- |
| 開發中 | **50%** | 已完成開案、進入開發但未完成 |
| 驗收中 | **75%** | 已交付並進入驗收但未完成驗收 |
| 已結案 | **100%** | 實質已完成，僅程序未走完 |

:::warning
**終止結算的最低落點為「開發中（50%）」。** 即使需求仍停留在 MVP 架構確認或開案確認階段，
一旦決定以終止開發結案方式結束並取得Scrum Master簽核，即依 50% 起算，不會低於此比例。
若不擬計費，應改以「**取消**」方式結束。
:::

### 該用哪一種？

| 情況 | 應採用 |
| -- | -- |
| 需求方撤回，雙方未就已投入工作量結算 | **取消需求** |
| 已投入實質工作量，雙方同意就該部分結算 | **終止開發結案** |
| 只是先停一下，將來可能再做 | **暫緩**（不屬提前結束） |
| 暫緩已久、確定不再進行且需結算 | 先**解除暫緩**，再發起**終止開發結案** |

# SP 計費與認列

![sp認列](https://hackmd.io/_uploads/S1q1sLnuzl.png)

### 計費基準
**專案費用 = 最終 SP × SP 單價**

### 分階段認列機制

SP 分三段認列，==**均於該關卡「通過後」才起算**==，而非開案即全額扣除：

| 觸發時點（通過後） | 本次認列 | 累計 | 對應平台狀態 |
| -- | -- | -- | -- |
| **① 開案確認 通過** | **50%** | 50% | 進入「開發中」 |
| **② 開發交付 通過** | **25%** | 75% | 開發中（首次 APP 交付經確認）<br>或 進入「驗收中」 |
| **③ 結案 完成** | **25%** | 100% | 「已結案」 |

**其他情形**
- 需求**暫緩**或**駁回**時，依其進入該狀態前已通過的關卡計算認列。
- 需求**取消**時，**全額釋放**已認列之 SP。
- SP 錢包之可用餘額 ＝ 年度配額 − 已認列 SP。

### 各階段之 SP 處理
| 階段 | 處理方式 |
| -- | -- |
| **開案** | 估算總 SP，作為專案基準。 |
| **執行** | SP 如有增減，一律循**設計變更**程序辦理，經第一關（Scrum Master＋需求窗口）與第二關（需求方逐條確認）通過後生效。 |
| **交付** | 需求方確認首次 APP 交付時，認列第二段的 25%（每案僅一次）；未確認者則於進入「驗收中」時認列，兩者擇一、不重複。 |
| **驗收** | 修復錯誤（bug）**不計費**，屬開發方品質責任。 |
| **結案** | 依已通過之設計變更自動結算，並經**Scrum Master簽核**後完成。 |
| **提前終止** | 循「終止開發結案」程序，經**Scrum Master簽核**依落點比例（50%／75%／100%）結算；單純取消則全額釋放、不計費。 |

:::warning
**與 v1.3 之差異：** 原「SP 增幅 10% 以內由 IT 裁決、超過 10% 由需求單位主管同意」之分級規則**不再適用**。現行流程中，**所有設計變更一律經Scrum Master於第一關背書**，不再依增幅比例分流。
:::
